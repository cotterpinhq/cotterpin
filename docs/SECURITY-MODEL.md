# Security model

What Cotterpin's guards defend against, in which install, and what they do not. Every hook rule, every approval and
every command that grants authority is held to this model; the tests named here pin each route.

Cotterpin has two installs. They differ in WHO the adversary is, and therefore in what must be out of that adversary's
reach.

## Developer mode

Cotterpin is installed in the developer's own user account (`pip install`, `cotterpin init`).

**The adversary** is an AI agent running as the same operating-system user, acting through its tools: the shell, the
file-edit and file-write tools, the read and search tools — every call of which reaches Cotterpin's hook
([HOOKS.md](HOOKS.md)) before it runs.

**What is required.** Every route THROUGH THE AGENT'S TOOLS AND COTTERPIN'S OWN COMMANDS to the following is refused —
by a hook rule at the destructive tier (a pending action only a person's signed approval turns into a run of that
exact action) or by the command itself:

**The approval itself** (ONE mechanism, [APPROVALS.md](APPROVALS.md)): a pending action records exactly what will
run; `cotterpin approve <id>` runs the root-owned signer through `sudo -k`, which shows the person the action itself
(every control character as a visible escape, so an escape sequence cannot hide what is signed) and signs it with an
ECDSA P-256 key only root can read. Hook actions, memory promotion, guard changes, false-positive marks and spend above
the cap all use these same records, this signer and these refusals.

**Out of scope, honestly.** Developer mode is a GUARDRAIL FOR AGENTS, not a sandbox. A process that never goes
through the agent's tools — malware already running as the developer, a build script the agent did not write but a
toolchain runs, the developer's own shell — is not judged by any hook, and can do anything that user can: edit the
user-owned stores, the licence, the installed package. What stays out of its reach is only what is root-owned: the
approval key and the signer (so it still cannot make an approval), and the operating system's authentication.
Specifically:

- a `--once` approval's spent state is kept in the user-writable approvals store and in the audit log; a process
  outside the agent's tools could set both back and reuse that ONE exact action within its 15-minute window;
- output a child process writes straight to its inherited file descriptors is not redacted by Cotterpin (only what
  Cotterpin itself prints is);
- a development checkout of Cotterpin (a git working tree outside `site-packages` and the release cache) is ordinary
  source code an agent edits as work; such a checkout can never set up approvals, because setup refuses a signer no
  release signature covers;
- with Touch ID enabled for sudo, the operating system's prompt names no action — the signer's own screen does (it
  shows the action and asks for a yes on the terminal before it signs);
- judging a program by its TEXT is a reading, not a proof. Cotterpin reads joined string pieces, environment lookups
  and encoded text in inline programs, and refuses a written program that names a guarded place; a program whose
  effect only exists at run time (it computes a path from data, or is a file the agent wrote and a test runner or
  `import` runs later without naming it) is confirmed by the developer when it is run directly, and is otherwise the
  residual a guardrail for agents has. Approvals stay safe regardless: they need the OS authentication and the root key;
- `cotterpin approvals setup` checks the signer against the release-signed digest computed by the installed Cotterpin
  (whose code the agent's tools cannot change, above) before running it as root; the bootstrap does not carry its own
  root-owned trust anchor, because none exists on a machine before setup. A hardened install's administrator installs
  the trust folder from a root-owned release instead.

**Runs of the product's routes.** A developer-mode repository runs the routes Cotterpin ships (the kernel's and the
installed packs') with the same trust root as `cotterpin check` and `cotterpin commit`: the INSTALLED runtime, which
the agent's tools cannot change (above). The run records that runtime file by file (`mode: developer`, the installed
version, the developer lock's digest) and every later step re-measures it, so a run is never continued on a changed
install (`runtime-identity-mismatch`) or in the other mode. Still refused under a developer lock: a policy that does not
say `mode: developer` or differs from the one the lock pins, an extension or adapter declaration (nothing pins it), a
route the repository registers itself (`developer-mode-product-routes-only`), and any developer lock on a hardened
machine — `tests/kernel/test_developer_mode_kernel_routes.py`.

## Hardened mode

An administrator installs Cotterpin root-owned, with an approved-release lock, and installs the security policy
`/private/etc/cotterpin/security.json` (macOS) or `/etc/cotterpin/security.json` (Linux), root-owned. Its presence
makes the machine hardened (`cotterpin.hooks.policy.hardened`): only root can create it, so no user file can make a
machine look hardened or stop it being one.

**The adversary** is everything in developer mode, AND a process that may write ANY user-owned file.

**What is required, and how it holds:**

| Requirement | How |
|---|---|
| licence, trust, signer, policy and lock live root-owned | the approval trust folder, the signer and the security policy are root-owned and read with `cotterpin.kernel.security.read_administrator_bytes` (root-owned all the way up, no group/other write, no granting ACL); the approved-release lock binds the root-owned publisher registry (`cotterpin.kernel.library`); the licence is not read at all — a hardened machine enforces by the administrator's policy, not by a user's licence file |
| enforcement cannot be lowered by deleting or editing user files | on a hardened machine the licence, consent and clock files never drop it to Watch (`cotterpin.release.licence_mode.standing` answers enforce), and `.cotterpin/hooks.json` never turns a sensitive or destructive rule down (`cotterpin.hooks.router.evaluate`) — `tests/hooks/test_hook_hardened.py` |
| approvals cannot be forged by writing user files | an approval is a signature by the root-only key; a record written by anyone else does not verify, whatever it says |
| the hook stays registered and runs the root-owned Cotterpin | `sudo cotterpin harden hooks install` (`cotterpin.kernel.managed_hooks`) registers the hook where only root can write: Claude Code's managed drop-in `/Library/Application Support/ClaudeCode/managed-settings.d/50-cotterpin.json` with `allowManagedHooksOnly: true` (a user or project `disableAllHooks` cannot turn managed hooks off), and Codex's admin-enforced `/etc/codex/requirements.toml` with `allow_managed_hooks_only = true` and `[features] hooks = true` pinned. Both run the root-owned launcher `/Library/Application Support/Cotterpin/bin/cotterpin-hook` by its absolute path; the launcher runs the hook with the supervisor's trusted framework Python in isolated mode (`-I -B -S`) on the root-owned release root, never a `cotterpin` on `PATH`. The release root must carry the installed language packs as well as the kernel: without them the hook cannot load its rules (measured). An existing `requirements.toml` that Cotterpin did not write is never overwritten; the administrator merges the block `cotterpin harden hooks render` writes. `cotterpin harden hooks status` reports each file as registered, missing, differs or unsafe (exit 0 only when everything is protected). **Grok is not covered:** it documents no administrator-managed hook registration, and its hooks are user-writable files that fail open. A hardened machine that allows Grok sessions does not protect their hook. Pinned by `tests/kernel/test_managed_hooks.py`: a scratch-root install and status run the same code path, and the launcher runs the real hook from a runtime root with nothing taken from `PATH`. The write as root to the real system folders, and a live Claude Code or Codex session reading them, are not run by the suite. |
| approvals bind to the hardware-key or SSO authority where configured | An administrator names the registered action `approval.grant` in the policy's `actionAuthorities` (only `hardware-key` or `oidc` authorities are accepted for it; a class or `default` rule never binds approvals by itself). From then on `cotterpin approve <id>` first asks the person's enrolled key (Touch ID through the signed platform helper, or a FIDO2 security key, with user verification) or the identity provider (a step-up login with MFA) for an assertion over exactly this approval: its id, its action digest, the scope and duration, the operator and a fresh nonce. The root-owned signer does not trust that process. It runs the existing authority verifiers (`HardwareKeyAuthority.verify`, with the root-owned signature counter; `OIDCAuthority.verify`, against the pinned issuer's keys) under the hardened install's root-owned runtime. The operator must be the account sudo authenticated. Only then does it sign, with the verified summary inside the signed approval. The hook honours an approval on such a machine only when that signed summary names one of the policy's `approval.grant` authorities. A policy that exists but cannot be read safely honours no approval. Pinned by `tests/kernel/test_approval_presence.py`: the real signer and verifier processes, real WebAuthn and OIDC signatures, replay, another action, another scope, another person, an unenrolled key and tampering are all refused; mutating out either check turns the tests red. Not run by the suite: root, sudo's prompt, a physical key and a Touch ID touch. A person enrols each key (`cotterpin auth hardware-key enrol`, then `sudo cotterpin auth hardware-key install-credential`). |

In hardened mode the one-run replay above is reachable by the stronger adversary too (both records it would set back
are user-owned): it bounds to re-running the ONE exact action a person approved, within 15 minutes of that approval.
